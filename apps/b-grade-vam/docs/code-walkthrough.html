Pendiente + VAM, calculadas a mano

Garmin ya trae VAM y pendiente nativas — pero Connect IQ no las expone por API. Este campo las reconstruye desde cero, solo con el altímetro barométrico y la distancia, y las muestra juntas en una celda. Este documento explica cómo, y por qué cada decisión rara es la correcta.

El rol honesto

El Edge 830 ya incluye de fábrica VAM, 30s VAM, Avg VAM, Lap VAM y pendiente. Un campo que solo repita eso no aporta nada. Por eso B existe por tres motivos concretos — y solo esos justifican usarla en la calle:

Dos métricas, una celda

Pendiente + VAM en un solo campo. En nativo son dos celdas separadas.

Ventana configurable

La VAM nativa es una media fija de 30 s. Acá elegís 5 / 10 / 30 s según lo reactiva que la quieras.

Zonas de color

La pendiente se lee de un vistazo, con guantes, por color — no por número.

Y, sobre todo, es el segundo proyecto Monkey C del autor: la primera app con algoritmos de verdad (buffers, filtros, suavizado, settings). El buffer de muestras que se construye acá es la base directa de las Opciones C (descenso), H (stamina) e I (test de subida).

La arquitectura: una regla que manda

Toda la matemática vive en módulos puros y testeables — sin Dc, sin Activity.Info, sin estado del device. La View es un wrapper fino que null-chequea las entradas y delega. Es el mismo patrón que la Opción A (TimeFormat ⟷ ActivityTimerView), pero escalado a ocho módulos.

SampleBufferpuro
Ring buffer de 64 muestras (t/d/h), cero allocations en régimen.
AltFilterpuro
Mediana-3, EMA y el gate de outliers con re-seed.
GradeMathpuro
100·Δh/Δd + guardas de parado y de rango.
VamMathpuro
Δh/Δt·3.6e6 + guardas de Δt y clamp.
RefSelectpuro
Elige la muestra de referencia: por distancia / por tiempo.

Transiciones del timer → acción; gate de muestreo.
Unitspuro
Conversión ft/h + strings (signo, redondeo, --).
GradeVamEnginepuro
Orquestador: junta todo lo anterior en un update().
GradeVamView
Wrapper fino NO testeable: lee, formatea, dibuja los 3 modos.
GradeVamApp
AppBase: entrega la View y reenvía onSettingsChanged.

¿Por qué tanta ceremonia? Porque compute() corre una vez por segundo durante horas y no se puede depurar en la montaña. Si la matemática es pura, se prueba entera y sin simulador — y la View queda tan chica que casi no tiene dónde esconder un bug.

El pipeline: de un dato a dos números

Cada segundo, GradeVamEngine.update(timerState, t, d, h, speed) hace esto, en orden:

  1. Transición de estado. ¿Arrancó, pausó, reanudó o reseteó? Decide la acción antes que nada.
  2. Gate. Solo se muestrea con el timer en ON. En pausa se congela.
  3. Mediana de 3 sobre la altitud cruda → mata un pico de una sola muestra.
  4. Gate de outliers contra la última muestra buena → ACCEPT / REJECT / RESEED.
  5. EMA (α=0,4) sobre lo aceptado → baja el ruido barométrico ~2×.
  6. Push de la terna {t, d, h_suavizada} al ring buffer.
  7. RefSelect + GradeMath / VamMath → la pendiente y la VAM actuales.

Las decisiones difíciles

Casi todo el diseño real está en los casos borde. Estas son las que parecen raras y no lo son:

AltFilter

Re-seed obligatorio

Un pico dura 1–2 muestras; una recalibración del baro o un túnel duran para siempre. Sin re-seed, el filtro rechazaría todo el resto de la salida. Regla: 3 rechazos seguidos → nueva línea base y se vacía el buffer.

EngineState

Reanudar = vaciar el buffer

En pausa, t y d se congelan pero la altitud sigue derivando. Conservar muestras pre-pausa fabricaría un pico (Δd≈0 con Δh real). Se tira todo; el costo es un warm-up de unos segundos.

RefSelect

Ventana de pendiente híbrida

Por distancia (20 m), pero con piso de 3 muestras. En un descenso a 40 km/h, una ventana pura de distancia degeneraría a una diferencia de 1 segundo, pura ruido.

VamMath

Guardas antes de dividir

Monkey C tira error de runtime al dividir por cero. Se exige Δt ≥ max(2 s, W/2) y ≥ 2 muestras antes de la división. Parado → 0 (dato válido), no ruido.

GradeMath

Fuera de rango → --

Si |grade| > 40 % es un error de datos. Se muestra --, no el valor clavado en 40: presentar un error como lectura real es peor que no mostrar nada.

disciplina de tipos

t es Number, no Float

Un Float de 32 bits pierde exactitud entera pasadas las ~4 h 40 m. El tiempo se guarda en ms enteros y la resta se hace en Number antes de convertir.

Units · View

Histéresis de display

El entero mostrado se mantiene hasta que el crudo se aleja más de 1 % del valor actual → no parpadea 7↔8 por el ruido del baro. El color de zona usa ese mismo entero, así número y color se mueven en lock-step.

Zonas de color

La pendiente se pinta por franja (setting on/off). Los tonos se adaptan al fondo del tema para mantener contraste; en pausa todo se atenúa a gris y las zonas se apagan.

≤ −3 bajando
−2…2 llano
3…7 verde
8…12 amarillo
≥ 13 rojo

Las bandas van sobre el entero que se muestra (no el valor crudo), así el color y el número siempre coinciden y no hay bordes solapados.

Y en un campo chico, en vez de elegir una sola métrica, se muestran las dos juntas y compactas — 7%/560 — con la pendiente en su color de zona. Si la celda tiene alto suficiente, aparece además un rótulo PEND/VAM arriba; si es muy chata, se omite y el número usa todo el espacio (el campo lo decide midiendo, no se asume). La VAM sigue las unidades del device — m/h en métrico, ft/h en imperial — igual que el campo VAM nativo de Garmin.

Cómo se prueba

Criterio de aceptación del repo: los unit tests en verde antes de la validación visual. Cada módulo puro tiene su *Test.mc con (:test) de Toybox.Test, que el compilador saca del release (costo cero contra los 128 KB). Se corren con “Monkey C: Run Tests”, perfil edge840 — y ya corrieron: 41 tests, 41 PASS, 0 fallos (compilando y ejecutando en el simulador, no solo revisando el código).

Un matiz que enseña algo. El caso “2 muestras → VAM 360” pasa por el pipeline completo, y el EMA atenúa el primer escalón de altitud (1 m crudo → ~0,4 m con solo dos muestras). Por eso el test de integración afirma la independencia de las guardas (pendiente null, VAM real y positiva), no un número clavado. El 360 exacto se prueba en VamMathTest, que es puro y no tiene EMA. Cada aserción, en la capa que le corresponde.

Depurar sin salir a andar

Con TEST_MODE = true en un build de debug, compute() ignora el sensor y consume un generador sintético: subida 7% → descenso −10% → llano, con ruido barométrico. Alcanza para ver los 3 modos de render, las zonas de color, la VAM negativa y el warm-up sin FIT ni device.

La clave está en que no deje rastro en el release — el mismo esquema que la Opción A: 

// const PLANO false: el optimizador -r elimina el bloque entero, llamada incluida.
private const TEST_MODE = false;

if (TEST_MODE) {           // se borra en release
    var syn = nextSynthetic();   // (:debug) real / (:release) stub vacío
    ...
}

La trampa sutil: nunca referenciar un miembro (:debug) fuera de una función (:debug). En release ese símbolo no existe y la compilación falla. Por eso el ascent sintético se devuelve desde nextSynthetic() en vez de leerse de un miembro dentro de compute().
