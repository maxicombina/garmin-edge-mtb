¿Vas por encima de tu media?

Un ciclocomputador Cateye de los viejos ponía una flechita al lado de la velocidad: apuntaba arriba si ibas más rápido que tu promedio, abajo si más lento, y desaparecía cuando coincidían. Este campo revive esa idea — y de paso muestra los dos números juntos, para leerlo de un vistazo. Este documento explica cómo, y por qué es la más simple de las tres apps del repo.

Speed km/h ▲24.3 AVG 21.7

El rol honesto

Garmin ya muestra velocidad actual y velocidad media — pero en celdas separadas. Ninguna combina las dos en un solo indicador de tendencia. Ese es el único motivo para usar este campo en la calle. Y tiene otras dos gracias:

La flecha del Cateye

Actual vs. promedio de la salida, con una flecha ▲/▼ al lado del número. Sin flecha cuando coinciden (la banda muerta). Feedback de esfuerzo de un vistazo, con guantes.

Casi gratis (Tier 1)

Para velocidad, Garmin ya calcula el promedio (averageSpeed). No hace falta buffer, ni suavizado, ni filtro — a diferencia de la Opción B. compute() es casi trivial.

Genérico por dentro

El módulo que decide ▲/▼/nada no sabe qué métrica compara. Sumar frecuencia cardíaca o cadencia mañana es escribir un adaptador nuevo, no tocar la lógica.

La arquitectura: dos módulos puros y una vista fina

Como en la A y la B, toda la lógica vive en módulos puros y testeables — sin Dc, sin Activity.Info, sin estado del device. La View es un wrapper fino que lee, formatea y dibuja. Pero acá hay mucho menos que orquestar: no hay buffer de muestras ni pipeline de suavizado (eso era necesario en la B porque calculaba pendiente y VAM desde cero; acá la métrica y su promedio llegan hechos).

TrendArrowpuro
Dos enteros ya redondeados → UP / NONE / DOWN. No sabe de qué métrica.
SpeedFormatpuro
m/s → km/h o mph, redondeo, y el string "24.3".
TrendArrowView
Wrapper fino NO testeable: lee, formatea, dibuja el valor + flecha + media.
TrendArrowApp
AppBase: entrega la View. Sin settings → ni siquiera onSettingsChanged.
TestUtil
Helpers de test (copia propia — nada se comparte entre apps).

Lo que cada segundo pasa por compute() es literalmente: leer las unidades del device, leer velocidad actual y media, redondear, comparar, formatear. Sin más.

  1. Unidades. paceUnits del device → km/h o mph (se relee cada tick: cambiarlas no avisa).
  2. Leer currentSpeed y averageSpeed de Activity.Info (m/s, pueden ser null).
  3. Redondear ambos a décimas con la MISMA función (shownTenths).
  4. Comparar los dos enteros → ▲/▼/nada (TrendArrow.classify).
  5. Formatear los strings de display; onUpdate() solo dibuja.

La banda muerta ES el redondeo

El único riesgo de este indicador es el parpadeo cerca del cruce: si vas justo a tu media, una micro-fluctuación cambiaría la flecha ▲▼▲▼ cada segundo. La solución no es suavizar la velocidad — es comparar sobre lo que el usuario ve. Se redondea una sola vez, y TrendArrow compara los enteros redondeados: 

function classify(shownCurrent, shownAverage) {
    if (shownCurrent == null || shownAverage == null) { return NONE; }
    if (shownCurrent > shownAverage) { return UP; }
    if (shownCurrent < shownAverage) { return DOWN; }
    return NONE;   // mismo entero mostrado -> sin flecha
}

Como el número de pantalla y la flecha salen del mismo redondeo, es imposible que se contradigan: si el número no cambió, no hay flecha. La banda muerta sale gratis, sin un umbral aparte. (Con 1 decimal se compara en décimas: 24.3 km/h es el entero 243.)

La flecha es DATO, no adorno

Acá hay una regla que invierte la de la Opción B, y es importante. En la B, el triangulito de "pendiente" es una decoración estática del label: siempre igual, pegado al rótulo, nunca al número. Regla dura: nunca junto al valor.

En la J es al revés a propósito: la flecha es el dato — cambia cada segundo según actual-vs-media, igual que el número — así que va pegada al valor, como en el Cateye. Se dibuja con primitivas dc (no un glifo de fuente: la cobertura del carácter flecha no está garantizada en los 13 devices). La de subir se reusa tal cual de la B; la de bajar es su espejo vertical exacto: 

// cabeza triangular (fillPolygon) + astil (fillRectangle)
function drawUpArrow(dc, x0, cyMid, w, h) {
    var top = cyMid - h/2;  var headBase = top + (h*55)/100;
    dc.fillPolygon([[x0 + w/2, top], [x0, headBase], [x0 + w, headBase]]);
    dc.fillRectangle(x0 + w/2 - stemW/2, headBase, stemW, h - headH);
}
function drawDownArrow(dc, x0, cyMid, w, h) {   // espejo: cabeza abajo, astil arriba
    var bot = cyMid + h/2;  var headTop = bot - (h*55)/100;
    dc.fillPolygon([[x0 + w/2, bot], [x0, headTop], [x0 + w, headTop]]);
    dc.fillRectangle(x0 + w/2 - stemW/2, cyMid - h/2, stemW, h - headH);
}

Gotcha reutilizable: fillPolygon espera una tupla [Numeric, Numeric]. Hay que pasar el literal [[x,y],...] sin cast — un as Array<Array<Number>> rompe el build (lección de la B).

Un decimal, una sola fuente

El valor va con 1 decimal, como el nativo. Acá hubo una duda real: ¿las fuentes numéricas del sistema (FONT_SYSTEM_NUMBER_*) tienen el glifo .? En la B se había asumido que no tenían el %, y por eso el % se dibuja en una fuente de texto aparte. Copiar ese truco para el punto habría sido lo "seguro".

En vez de asumir, se verificó: una app de prueba desechable dibujando 12.3, 12,3, 12:34, -12 y 12%3 en esa fuente, corrida en el simulador. Renderizan todos — punto incluido. Así que el valor se dibuja como un solo string en una sola fuente, sin partirlo. Más simple que la B.

Verificado en el simulador (perfil edge840), no en hardware físico — el estándar que el repo usa para decisiones de fuente, pero pendiente de una confirmación eventual en device. (De paso dejó anotado que quizás la B tampoco necesitaba partir el % — pero eso no se toca sin pedirlo.)

El render: un valor grande + su media

Una sola métrica protagonista, así que — como la A — la adaptación es continua: una escalera de fuentes elige la más grande que entra, con la selección cacheada (solo se re-mide si cambia el tamaño de celda o la unidad). Sobre eso, dos añadidos:

Valor + flecha, centrados

El grupo [flecha + número] se centra. Si la flecha no entra (celda muy angosta) se descarta con gracia y queda el número solo — nunca se pierde el dato principal.

Media en una línea aparte

Si la celda es alta (AVG_MIN_H), debajo aparece AVG 21.7 más chico, sin flecha (es la referencia). Si no hay lugar, se omite: sigue siendo un indicador útil.

Los aprendizajes de fuentes de A/B se heredan tal cual: FONT_SYSTEM_NUMBER_* para los dígitos, FONT_GLANCE para el label, y el centrado óptico por descent/2 (las fuentes numéricas reservan un descendente que los dígitos no usan). La unidad va en el label (SPEED KM/H), como el VAM M/H de la B.

Criterio del repo: los unit tests en verde antes de la validación visual. Los dos módulos puros tienen su *Test.mc con (:test) de Toybox.Test (excluidos del release). Corren con "Monkey C: Run Tests" — y ya corrieron: 9 tests, 9 PASS.

Además, un review adversarial de tres lecturas independientes (conformidad con la spec, correctitud y casos borde, release-safety y convenciones) comparó el código contra la spec y contra la Opción B, y no encontró nada. Compila limpio para edge840 y edge830.

Depurar sin salir a andar

Con TEST_MODE = true en un build de debug, compute() ignora el sensor y consume un generador sintético que recorre un perfil de velocidades. La clave: acumula su propia distancia y tiempo y calcula el promedio como lo hace Garmin (dist / tiempo), así la media converge de forma realista a lo largo del ciclo — y se ven las tres flechas (arriba en los tramos rápidos, abajo en los lentos, nada en el cruce) conviviendo con el número de la media, que es justo lo que hay que validar de un vistazo.

El flag vive en false en el repo (se pone en true solo mientras se depura, y nunca llega a un release). El esquema de exclusión es el mismo de A/B: const plano → el optimizador borra el bloque, y las funciones de debug van en pares (:debug)/(:release).
